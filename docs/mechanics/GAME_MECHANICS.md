## 0. Как читать этот документ

Документ содержит полные спецификации всех геймплейных механик. Каждый раздел `MECH-XX` даёт: назначение и дизайн-критерий (что должно чувствоваться игроком), формальные правила (числа, формулы, машины состояний), поток выполнения с точки зрения сервера, edge cases и доказательную базу из референсов. Все времена в документе — **игровые** (06:00–06:00 следующего дня), если не сказано «реального времени» (РТ). Глобальные часы — на сервере; клиенты синхронизируются polling'ом каждые 15–30 с.

## MECH-01. Сутки и глобальный игровой цикл (SIM)

### 1.1 Назначение и дизайн-критерий

Глобальный цикл день/ночь — ритм всей игры: ночью **только** вылазки, днём — убежище, и все игроки мира живут по одним часам. Это превращает Telegram-уведомления («началась ночь — пора на вылазку») в ежедневный ритуал. Дизайн-критерий: игрок должен всегда знать текущую фазу и остаток времени до её смены, а серверный тик должен выполняться детерминированно, без ручных действий игрока.

Это прямая адаптация цикла This War of Mine, где день длится с 06:00 до 20:00, а ночь — с 21:00 до 05:00, с предупреждениями о смене фазы около 19:50 и 04:20 [1]. Мы масштабируем 6-минутный цикл TWoM до 4-часового реального цикла, сохраняя пропорции фаз и окна предупреждений.

### 1.2 Формальные правила

Один игровой день = 4 часа реального времени. Календарь суток:

| Фаза | Игровое время | Реальная длительность | Доступные действия |
|---|---|---|---|
| Утро (сводка) | 06:00–08:00 | 20 мин РТ | Приказы персонажам, сбор урожая, лечение, торговля NPC |
| День | 08:00–20:00 | 2 ч РТ | Крафт, постройки, торговля, отдых персонажей, рынок |
| Сумерки | 20:00–21:00 | 10 мин РТ | Только назначение вылазки: локация, персонаж, снаряжение |
| Ночь | 21:00–05:00 | 1 ч 20 мин РТ | Только вылазки и защита убежища; убежище «закрыто» |
| Утренний тик | 05:00–06:00 | 1 ч РТ (буфер) | Сервер: потребление ресурсов, применение состояний, мировые события |

Важно: игровой тик выполняется **один раз** в 05:00 игрового времени (серверный cron, UTC-расчёт по глобальным часам). Игровые часы — виртуальные; реальная длительность фаз выше приведена для ориентира игрока и расчёта таймеров UI.

Правила доступа по фазам (проверять на сервере при каждом действии):

1. **Дневные действия** (крафт, постройки, лечение, отдых, NPC-торговля) разрешены только в фазе «утро–день» (06:00–20:00). В сумерках и ночью — отказ с кодом `DAY_ACTIONS_LOCKED`.
2. **Вылазка** может быть назначена только в фазе «сумерки» (20:00–21:00) и исполняется сервером в фазе «ночь». В 05:00 все активные вылазки принудительно завершаются (персонаж возвращается, добыча фиксируется, неполученные ноды теряются).
3. **Рынок и аукционы** работают круглосуточно, но торговые сделки, выставленные ночью, исполняются утром 06:00 (покупатель получает товар и тратит талоны утром — это исключает гонку с «последним кликом» ночью).
4. **Уведомления** (бот): push в 20:00 («Скоро ночь — назначьте вылазку»), 21:00 («Началась ночь»), 06:00 («Новое утро — сводка за сутки»).

### 1.3 Поток серверного тика (05:00 игрового времени)

![Цикл суток](/docs/mechanics/assets/day_night_cycle.png)

Тик выполняется для каждого игрока в фиксированном порядке (важен — раненые применяются после потребления):

1. **Завершить вылазки**: все активные `raid_session` с `status=open` переводятся в `status=resolved_no_return` (персонаж вернулся без части добычи, см. MECH-04, edge case E4).
2. **Потребление ресурсов** по формуле RES-02: вода и еда списываются с общего склада убежища в пользу каждого живого персонажа. Если ресурса не хватает — персонаж получает состояние голода (CH-02).
3. **Применить состояния**: продлить раны/болезни, проверить смерть/уход персонажей, восстановить энергию спящим.
4. **Пассивные здания** (сборщик воды, сад, ловушки): произвести и зачислить ресурсы по формуле SH-04.
5. **События**: сгенерировать/применить мировое событие (EVT), если день совпадает с расписанием.
6. **Исполнить рынок**: матчинг лотов (MKT-02).
7. **Обнулить суточные счётчики**: число вылазок, дневные действия.

### 1.4 Формат данных сервера

```json
{
  "world_clock": { "day": 37, "hour": 6, "phase": "morning", "next_phase_at": "2026-08-14T20:00:00Z" },
  "player_state": { "tid": 37, "survivors_alive": 2, "night_raid_available": true }
}
```

`world_clock` отдаётся при любом polling-запросе (ответ сервера содержит часы), чтобы клиент мог показать оставшееся время фазы без отдельного запроса.

### 1.5 Edge cases

| # | Случай | Поведение сервера |
|---|---|---|
| E1 | Игрок офлайн сутки | Тик применяется при следующем входе ретроспективно по `world_day` (симуляция «за кадром»); персонажи, умершие в отсутствие, помечаются; офлайн-сводка приходит ботом при входе |
| E2 | Два тика подряд из-за сбоя cron | Идемпотентность по `world_day`: повторный тик — no-op (журнал `world_ticks` с unique-ключом по `world_day`) |
| E3 | Часовой пояс игрока | Не учитывается: мировые часы едины (UTC), фаза определяется глобально, как в EVE Online |
| E4 | Персонаж не вернулся к 05:00 | Вылазка завершается принудительно: добыча до текущего нода засчитывается, персонаж возвращается раненым (−20 HP), мораль −10 (TWoM: опоздавшие приходят позже днём, возможно ранеными [2]) |

### 1.6 Доказательная база и адаптация

This War of Mine делит сутки на день (06:00–20:00) и ночь (21:00–05:00) с равными реальными длинами 6 минут и предупреждениями фаз [1]. Мы адаптируем: (а) растягиваем до 4 часов для асинхронного Telegram-жанра, (б) добавляем фазу «сумерки» (10 мин РТ) как окно назначения вылазки — в TWoM назначение происходит перед ночью, у нас оно ограничено временным окном для MMO-синхронизации, (в) фиксируем точку потребления ресурсов утром (тиком), а не в момент действия игрока — это сервер-аутентитет и защита от читов.

### 1.7 Технические заметки (обзор)

Тик реализован как платформенный Heartbeat-cron (`/api/sim/world_tick`), запускающий функцию `WorldTicker.tick(world_day)` в одной транзакции PostgreSQL (`REPEATABLE READ` по `world_day`). Уведомления шлёт aiogram-бот после успешного тика (batch-запрос `sendNotification` с rate-limit). Детальная сетевая спецификация — в разделе 1.8–1.13.

## MECH-01A. Сетевой протокол и синхронизация серверных тиков (NET)

Раздел является частью MECH-01 и обязательный для реализации: бэкенд (FastAPI) обязан следовать протоколам ниже без отклонений, так как MECH-01 полагается на детерминизм тика и единые мировые часы.

### 1.8 Модель времени на сервере

Мировые часы хранятся единственным источником истины: таблица `world_clock { world_day int8 PRIMARY KEY, day_started_at timestamptz NOT NULL }`. Строка с `world_day = N` существует ровно в диапазоне: начало дня N = `2026-08-14T02:00:00Z + (N-1) × 4 ч` (первый игровой день стартует в заранее оговорённую UTC-дату — см. `.env.example`), конец дня N = начало дня N+1. **Запрещено** хранить фазу как отдельное поле: фаза выводится из `(now − day_started_at) mod 4 ч` по таблице ниже и пересчитывается при каждом запросе.

| Игровое время | Смещение от начала дня | Фаза |
|---|---|---|
| 05:00 | 0 с (момент тика) | `tick_window` (буфер утреннего тика) |
| 06:00–08:00 | 0–7200 с | `morning` |
| 08:00–20:00 | 7200–50400 с | `day` |
| 20:00–21:00 | 50400–54000 с | `dusk` |
| 21:00–05:00 | 54000–82800 с | `night` |

Момент смены фазы в UTC для клиента: `phase_change_at = day_started_at + смещение`. Сервер гарантирует монотонность `world_day` (только +1 при смене суток, никогда возврат или скачок — если реальное время «перепрыгнуло», день N отмечается пропущенным, тик для него выполняется мгновенно, см. 1.10).

### 1.9 Аутентификация и идентификация запроса

Все запросы к игровому API проходят через Telegram `initData` (Mini App) или `telegram_id` (бот-обёртка). Middleware FastAPI: (1) валидирует HMAC-подпись `initData` (ключ `WEBHOOK_SECRET` из .env, срок жизни подписи ≤ 1 ч — проверка `auth_date`), (2) резолвит `player_id` по `telegram_id`, (3) добавляет в контекст запроса. Без валидной подписи — `401 INVALID_INIT_DATA`. Каждый игровой мутационный запрос (вылазка, крафт, постройка, лот) — отдельная транзакция с серверной проверкой фазы **внутри** той же транзакции (снимок `now` = `statement_timestamp()`, не время клиента). Часы клиента на сервере не доверяются никогда: все временные метки игровых событий пишет сервер.

### 1.10 Серверный тик: контракт, идемпотентность, ретроспектива

**Контракт Heartbeat-cron** (платформа): вызов `POST /api/sim/world_tick` с телом:

```json
{ "secret": "<CRON_SECRET из .env>", "world_day": 37, "fired_at": "2026-08-15T05:00:00Z" }
```

Правила обработки на сервере: (1) эндпоинт доступен только из внутреннего диапазона (проверка `CRON_SECRET` + ограничение по source IP); (2) `WorldTicker.tick(world_day)` открывается в одной транзакции `REPEATABLE READ` с advisory lock `pg_advisory_xact_lock('world_tick', world_day)` — параллельный запуск двух инстансов тика для одного дня блокируется, а не дублируется; (3) журнал `world_ticks { world_day PK, started_at, finished_at, status, affected_players, replay_log_ref }` — уникальность по `world_day` гарантирует: повторный вызов с тем же `world_day` до `finished_at = NULL` (висит) возвращает `409 TICK_IN_PROGRESS`, после `finished_at IS NOT NULL` — `200` с телом `{ "status": "already_applied" }` (no-op, идемпотентность, E2);
(4) **доверие к параметру `world_day` условное**: сервер сверяет `fired_at` с ожидаемым окном (±15 мин от начала `tick_window` дня N); при несовпадении вычисляет `world_day` сам по `day_started_at` и берёт своё значение, логируя расхождение (`WARN clock_drift`);
(5) тик обязан завершаться ≤ 5 минут реального времени (лимит `statement_timeout` 300 с на cron-роль); сверх лимита — откат транзакции и сигнал алерта (мониторинг платформы).

**Ретроспективный тик (E1, офлайн-игрок)**. Глобальный тик исполняется для мира независимо от онлайна (все игроки), поэтому «нагнать пропущенные дни» игроку не нужно в общем случае. Ретроспектива затрагивает только **неприменённые персонально-адресованные эффекты**: если игрок не заходил N дней, при первом входе сервер исполняет очередь персонально-адресованных событий (набеги, в которых игрок был целью по журналу EVT-«цели», отложенные награды из MOR, просроченные лоты с холдом — освобождение). Реализация: таблица `pending_player_events { id, player_id, world_day_due, payload_json, applied bool }` с индексом `(player_id, world_day_due)`; при `GET /api/me/state` после пропуска ≥1 дня сервер атомарно вычитывает очередь до `world_day_due ≤ current_day` и возвращает сводку.

**Пропущенные мировые дни**. Если cron не отработал день N и сервер обнаружил пропуск (сверка `world_day` по реальному времени при следующем heartbeat), сервер исполняет `tick(N)`, затем `tick(N+1)`… до актуального дня в одном Heartbeat-вызове, либо пропускает их (в зависимости от флага `.env` `CATCHUP_MODE = full|skip`): `full` — мир не отстаёт от реального времени (рекомендуется), `skip` — дни отмечаются пропущенными, игроки «теряют» сутки (использовать только при аварии, с публикацией в новостной ленте Mini App). Дефолт: `full`.

### 1.11 Протокол синхронизации клиента: polling, обратный отсчёт, расходимость

Клиент (React Mini App) не держит постоянное соединение: Telegram-экосистема и асинхронный жанр делают polling достаточным и дешевле WebSocket по ресурсам сервера.

**Цикл polling**: (1) клиент при монтировании и после каждого фазового перехода вызывает `GET /api/me/state` (полный снимок состояния + `world_clock`); (2) в остальное время — лёгкий heartbeat `GET /api/sim/clock` каждые 30 с (только `world_clock` + `player_state.heartbeat`), не меняющий состояние игрока; (3) при возвращении вкладки в фокус (`visibilitychange`) — немедленный полный снимок, чтобы «пропущенный» во время свёрнутой вкладки тик отобразился сразу.

**Формат `GET /api/sim/clock`**:

```json
{
  "clock": {
    "world_day": 37,
    "phase": "night",
    "now": "2026-08-15T01:12:44Z",
    "next_phase_at": "2026-08-15T05:00:00Z",
    "server_skew_ms": 42
  }
}
```

**Расчёт обратного отсчёта на клиенте** (без доверия к локальным часам): клиент один раз при каждом heartbeat замеряет расхождение `skew = server_now − client_now` (поле `server_skew_ms`), затем считает `time_left = next_phase_at − (client_now + skew)`. Таймер пересчитывается только локально между heartbeat'ами. При расхождении локального обратного отсчёта с серверной фазой >15 с (клиент «проспал» тик) — принудительная полная синхронизация `GET /api/me/state` и перерисовка экрана с баннером события тика (сводка/ночь), чтобы игрок не действовал по устаревшей фазе.

**Защита от действий в «устаревшей» фазе**: клиент блокирует кнопки по локальному таймеру, но последнее слово — серверный код отказа (`DAY_ACTIONS_LOCKED`, `RAID_NOT_IN_DUSK`, `RAID_TOO_TIRED` и т. п.). Клиент обязан отображать точный текст кода отказа из таблицы ошибок (1.13) — не generic «ошибка».

### 1.12 Конфликтующие действия и серверная валидация (консистентность сессий)

Все клиентские действия передаются как **интенты**, сервер отвечает результатом — клиент никогда не считает действие выполненным до `2xx`.

**Инвариант фазовых действий**: каждое мутационное действие проверяет фазу внутри своей транзакции (SELECT фазы с `FOR SHARE` на `world_clock` — строка-одиночка, не блокирует запись), поэтому «окно» между проверкой на клиенте и исполнением на сервере не создаёт гонку: сервер всегда прав, клиент только эвристика UX.

**Сессия вылазки (привязка к MECH-04)**: создаётся `POST /api/raid/start { location, character_id, loadout }` только в фазе `dusk`; ответ — `raid_session_id` + первичный нод. Каждое действие нода — `POST /api/raid/{session}/node/{n}/act { intent }` с серверной валидацией: сессия `open` + owner + текущий нод = `n` (нельзя «вернуться» к нодам назад или перепрыгнуть — `400 INVALID_NODE_SEQUENCE`). Досрочный выход — `POST /api/raid/{session}/leave` (E5 MECH-04). Если игрок закрыл вкладку — сессия остаётся `open` на сервере; следующий вход (полный снимок) возвращает активную сессию с текущим нодом и флагом `can_resume`; таймер `next_phase_at = 05:00` на клиенте означает: сессия будет принудительно закрыта сервером в 05:00, клиент предупреждает «Вернитесь до рассвета».

**Дневные действия с суточными счётчиками** (1 действие крафта/постройки на слот в сутки): сервер хранит `daily_action_log { day, scope, action }` с unique-ключом; повторное действие того же скоупа в тот же день — `409 DAILY_LIMIT_REACHED` (идемпотентный отказ, не ошибка).

**Политика при отключении сети**: действия накапливаются в очереди на клиенте максимум 5 с (после — дисклард с уведомлением «сервер недоступен»), потому что игровые действия по времени критичны (окно сумерек 10 мин РТ), а отложенная отправка «старых» интентов нарушила бы валидность фазы. Вылазка — исключение: действия нода не кэшируются вовсе (сразу сетевой вызов с retry только при `5xx`/таймауте, не при `4xx`).

### 1.13 Протокол ошибок и уведомления

Единый формат ошибки: `{ "error": { "code": "RAID_NOT_IN_DUSK", "message": "Вылазку можно назначить только в сумерках (20:00–21:00)", "retry_after_s": null } }`. HTTP-коды: `400` — нарушение правил (фаза, лимит, вес), `401/403` — авторизация, `404` — несуществующий объект, `409` — конфликт (идемпотентные лимиты, race на рынке `LISTING_SOLD`), `429` — rate-limit, `500` — только внутренние аварии, клиент показывает generic-баннер. Таблица игровых кодов, обязательная к реализации:

| Код | Ситуация | Клиентский текст |
|---|---|---|
| `DAY_ACTIONS_LOCKED` | Дневное действие ночью/в сумерках | «Действие недоступно ночью. Дождитесь утра» |
| `RAID_NOT_IN_DUSK` | Назначение вылазки вне окна 20:00–21:00 | «Вылазка назначается только в сумерках» |
| `RAID_TOO_TIRED` | Энергия персонажа < 25 | «{Имя} слишком устал для вылазки» |
| `RAID_WEIGHT_EXCEEDED` | Предмет сверх лимита рюкзака | «Не влезает: {вес}/{лимит} кг» |
| `RAID_NO_RETURN` | Тик 05:00 закрыл сессию | «{Имя} вернулся под утро, ранен. Добыча сохранена» |
| `DAILY_LIMIT_REACHED` | Повторное суточное действие | «Сегодня уже использовано» |
| `STORAGE_FULL` | Склад переполнен при выдаче лута | «Склад полон. Продайте или выбросите лишнее» |
| `LISTING_SOLD` | Лот уже выкуплен | «Лот уже куплен другим игроком» |
| `INVALID_NODE_SEQUENCE` | Неверный порядок нодов | «Синхронизация вылазки… обновите экран» |
| `TICK_IN_PROGRESS` | Повторный heartbeat тика | (только логи, клиент не видит) |

**Уведомления (бот + Mini App)**: источник — событие тика (не клиент). После успешного `tick(world_day)` бот шлёт batch-уведомления `sendNotification` (Telegram Bot API, rate-limit 1 сообщение/с на бота — batching по группам игроков ≤ 30 сообщений/пакет, пауза между пакетами). Уведомления дублируются в ленту новостей Mini App (`GET /api/news`, журнал последних 7 суток) — игрок, отключивший пуши, не теряет сводку. Персонально-адресованные уведомления (набег, дилемма, рынок) шлются немедленно после применения эффекта, не ждут следующего тика.

### 1.14 Требования к тестированию сетевой части

(1) Unit: генератор фаз из `(day_started_at, now)` на граничных значениях смещений (±1 с вокруг каждой смены фазы); (2) интеграция: два параллельных heartbeat с одинаковым `world_day` → ровно один тик применён (`world_ticks.finished_at` у одного); (3) интеграция: heartbeat с `fired_at` вне ±15 мин → сервер берёт свой `world_day`, лог `clock_drift`; (4) e2e: клиент с искусственным `skew = −30 с` выполняет действие на границе фазы → сервер отклоняет по своей фазе, клиент показывает точный код из 1.13; (5) нагрузочный: тик для 10 000 игроков ≤ 300 с (cron-роль) — иначе `CATCHUP_MODE` переключается вручную. Все числа — для `balance_sim.py`-согласованной конфигурации из MECH-05 (2 персонажа/игрок, 1 вылазка/ночь).

## MECH-02. Персонажи: выжившие, состояния, смерть (CH)

### 2.1 Назначение и дизайн-критерий

Персонажи — эмоциональное ядро игры: игрок отвечает за конкретных выживших с именами, характерами и судьбами. Дизайн-критерий: смерть персонажа должна ощущаться как потеря (персонаж «ушёл» с историей, а не «юнит удалён»), а состояния (голод, болезнь, рана, мораль) должны быть понятны по числовым порогам, без скрытой математики.

### 2.2 Формальные правила

**Старт**: игрок начинает с 2 персонажами (критерий приёмки плана). Максимум 2 базовых слота + 1 слот за приглашённого выжившего + дополнительные за Stars. Новый персонаж на вылазках даёт −30% эффективности в первые 2 суток (адаптация).

Модель персонажа на сервере:

```json
{
  "id": "char_8f2",
  "player_id": 123,
  "name": "Марина",
  "age": 34,
  "trait": "medic",
  "states": {
    "health": 100,
    "energy": 100,
    "hunger_stage": 0,
    "hunger_days": 0,
    "morale": 62,
    "wounds": [],
    "sick_days": 0
  },
  "status": "active"
}
```

**Черты (trait)** — одна на персонажа, выбирается при старте/найме. Каждая даёт ровно один пассивный эффект:

| Черта | Эффект | Влияние на баланс |
|---|---|---|
| `medic` | Лечение дешевле: −1 доза медикаментов на лечение | Экономит редкий ресурс |
| `strong` | Вес рюкзака +5 кг в вылазке | Прямой буст добычи |
| `fast` | В вылазке +1 нод за ночь (глубина 9→10) | Больше попыток, но не больше добычи за нод |
| `quiet` | Шанс встречи с враждебным NPC в вылазке −15% | Снижает риск |
| `negotiator` | Бонус +10% к получаемым талонам на рынке | Экономическая |
| `optimist` | Падение морали замедлено на 20% | Психологическая |

**Состояния** — дискретные стадии (не непрерывные шкалы, как в TWoM): здоровье и энергия — шкалы 0–100; голод, раны, болезнь, мораль — стадии/порты.

### 2.3 Машина состояний голода

![Машина состояний персонажа](/docs/mechanics/assets/character_states.png)

Переходы (происходят в утреннем тике MECH-01, когда не хватает еды/воды):

| От | До | Условие | Эффект |
|---|---|---|---|
| OK | `hungry` (стадия 1) | 1 сутки без еды | Мораль −5/сутки в этом состоянии |
| `hungry` 1 | `hungry` 2 | 2 суток без еды | Эффективность действий −10% |
| `hungry` 2 | `very_hungry` (1) | 3 суток без еды | Усиливает раны/болезнь (+1 день длительности); действия −20% |
| `very_hungry` | `starving` | 5 суток без еды | Другие персонажи грустят (мораль −3/сутки всем в убежище); шанс ухода из группы |
| `starving` | `extremely_starving` | 7 суток без еды | Шанс ухода 15% за сутки (если есть рана/болезнь — 30%) |
| `extremely_starving` | `dead` | ещё 1 сутки без еды | Смерть, необратима |

Полная порция (`cooked_meal`, см. RES-02) откатывает голод на 1 стадию назад и обнуляет `hunger_days`. Кормление — по формуле: персонаж сыт → стадия уменьшается через 1 сутки после порции. Вода действует мгновенно: 1 сутки без воды = сразу `very_hungry` (вода критичнее еды, по Day R вода расходуется вдвое быстрее еды [3]).

### 2.4 Усталость, раны, болезни

**Энергия**: 100 = отдохнувший. Ночь сна в кровати восстанавливает 100% (без кровати — 70%). Вылазка тратит 25, работа у станка 10, лечение другого персонажа 15, ремонт/постройка 15. Персонаж с энергией <25 не может идти на вылазку (TWoM: exhausted не участвует [2]).

**Рана**: `wounds: [{type: "light|heavy", days_left}]`. Лёгкая рана: 1 сутки отдыха + бинт (не обязательно, но ускоряет на 1 сутки). Тяжёлая: 3 суток + обязательный бинт, иначе переход в `infected` (см. ниже). Энергия восстанавливается на 50% медленнее, пока ранен.

**Болезнь**: шанс 5% при использовании грязной воды (см. RES-02), шанс 10% при тяжёлой ране без бинта. Длительность 3 суток + лечение медикаментами (1 доза снижает на 2 суток). Без лечения: `wounded` → `critically_sick` (5 суток) → `dead`.

**Мораль**: шкала 0–100. Падает от голода, раны/болезни соседей, негативных моральных выборов (MECH-06). При морали <20 персонаж получает статус `depressed`: отказывается от вылазок 2 суток (его можно уговорить: бонус мораль +10 за полный рацион + отдых сутки). При морали = 0 — персонаж покидает группу (перманентно) с сообщением-прощанием.

**Смерть**: необратима. Персонаж переходит в статус `dead`, его слот освобождается через 1 сутки («место ушло с телом» — новый выживший не может присоединиться раньше). Смерть персонажа: мораль −15 всем остальным (TWoM: соседи грустят по умершему [4]).

### 2.5 Доказательная база и адаптация

TWoM использует дискретные стадии голода (Well fed → Normal → Hungry ×2 стадии → Very Hungry ×2 → Starving → Extremely Starving → смерть через сутки) с правилом «полная порция откатывает на стадию назад» [4]. Мы переносим стадии и правило отката, но (а) ускоряем прогрессию: в TWoM до смерти ~8 дней без еды, у нас — 8 суток игровых = 32 часа РТ, что создаёт ощутимое давление без жестокого наказания за одну пропущенную сессию, (б) добавляем воду как отдельный критический ресурс (в TWoM воды нет — это наша адаптация под дефицит Day R [3]), (в) заменяем «уход из группы» TWoM (персонаж уходит со своими вещами) на шанс ухода с возможностью уговора через мораль — для удержания F2P-игрока.

### 2.6 Технические заметки

Все переходы состояний — только в утреннем тике (сервер-аутентитет). Клиент показывает стадии цветовой индикацией (зелёный/жёлтый/оранжевый/красный) и точный текст: «Марина голодна 2 сутки, на 3-й сутки станет Очень голодной». История состояний пишется в `character_events` — используется для генерации «истории персонажа» (нарративный фидбек, см. план проекта: механики как фундамент нарратива [5]).

## MECH-03. Убежище: постройки и крафт (SH)

### 3.1 Назначение и дизайн-критерий

Убежище — долгосрочный прогресс: игрок вкладывает материалы в здания, а здания снижают ежедневное давление выживания. Дизайн-критерий: каждое здание должно иметь измеримый суточный эффект, который игрок может пересчитать в «сколько вылазок экономит»; ни одно здание не должно быть строго обязательным (нет единственного «win condition»-постройки).

### 3.2 Формальные правила

Убежище — набор слотов (старт: 4 слота). Здание занимает слот, имеет уровни (tier 1–3), строится за материалы и время (в игровых сутках). Прогрессия tiers по материалам как в Last Day on Earth: дерево → обработанные материалы → металлолом, с экспоненциальным ростом стоимости [6].

| Здание | Слоты | Стоимость tier 1 | Время постройки | Суточный эффект | Tier 2 | Tier 3 |
|---|---|---|---|---|---|---|
| Кровать | 1 | 20 материалов | 1 сутки | Спящий восстанавливает 100% энергии (без — 70%); +1 слот сна | +1 сон за ночь | Раненые лечатся на 1 день быстрее |
| Печь | 1 | 25 материалов + 5 топлива | 1 сутки | Готовка `cooked_meal` (см. RES-02); +1 готовка за сутки | +1 готовка | Дешевле топливо на 25% |
| Сборщик воды | 1 | 30 материалов | 2 суток | +2 чистой воды за сутки (дождь: +3) | +3 воды | +4 воды, фильтр бесплатный |
| Верстак | 1 | 35 материалов | 2 суток | Крафт инструментов (лом, фонарь, сумка); 1 крафт/сутки | 2 крафта | Крафт оружия (MVP: не включено) |
| Аптечка (стеллаж) | 1 | 30 материалов | 1 сутки | Раны лечатся −1 сутки; шанс болезни при грязной воде −50% | Раны −2 суток | Бесплатный бинт при ране |
| Сад (грядка) | 1 | 20 материалов + 5 воды/сутки | 2 суток | +1 сырая еда за 2 суток после полива; без полива 3 суток — погибает | +1 еда/сутки | +2 еды, нужен 1 рабочий |
| Ловушка (силки) | 1 | 15 материалов | 1 сутки | +0.5 сырой еды за сутки (пассивно, даже ночью) | +1 еда | +1 еда + 1 мех. деталь |

**Строительство**: закрывается на 1 игровой день («строится до завтра») — занимает слот, не даёт эффекта, не может быть отменено с возвратом ресурсов в первый день (с 50% возвратом со второго дня). Это даёт время на «одуматься» и экономит серверные анимации.

**Ремонт**: здания изнашиваются от мировых событий (набег мародёров: −1 уровень или поломка с вероятностью 40%). Починка стоит 50% от стоимости tier 1 + 1 сутки.

**Материалы**: обобщённая единица `materials` (tier 1), `parts` (tier 2, из вылазок на промзоне), `scrap` (tier 3, редкие локации/рынок). Конверсия: 10 `materials` → 1 `parts` на верстаке, 5 `parts` → 1 `scrap`.

### 3.3 Крафт-рецепты (верстак)

| Рецепт | Вход | Выход | Время |
|---|---|---|---|
| Лом | 8 материалов | 1 лом | 0.5 суток |
| Фонарь | 5 материалов + 1 топливо | 1 фонарь | 0.5 суток |
| Сумка-рюкзак | 10 материалов | +3 кг рюкзака | 1 сутки |
| Бинт | 3 материала + 1 травы (вылазка) | 1 бинт | 0.5 суток |
| Фильтр воды | 4 материала + 1 уголь | 1 фильтр (10 использований) | 0.5 суток |
| Конвертация tier 1→2 | 10 материалов | 1 parts | 1 сутки |
| Конвертация tier 2→3 | 5 parts | 1 scrap | 2 суток |

### 3.4 Сводка суточной экономики убежища

Минимальное устойчивое убежище (2 персонажа): сборщик воды (2 воды/сутки) покрывает 50% водопотребности (4/сутки), сад + ловушка дают ~1 сырую еду/сутки против потребления 2 — остальное из вылазок. Это осознанный баланс: здания снижают давление, но не устраняют вылазки — ночные рейды остаются смысловым ядром (см. баланс-симуляцию `balance_sim.py`).

### 3.5 Доказательная база и адаптация

TWoM: станции специализированы (печь — еда, сборщик дождевой воды — до 4 воды за цикл ожидания, верстак — инструменты, грядка — еда) [7]. LDOE: тайловая база с тирами материалов и экспоненциальной стоимостью [6]. Адаптации: (а) у нас нет инвентаря тайлов — здания как объекты-слоты (проще UI Mini App), (б) время постройки в игровых сутках вместо реальных таймеров (жанр-специфика: игрок заходит 1–2 раза в сутки, таймер на 30 минут реала пропал бы), (в) износ от мировых событий связывает SH с EVT — здания не вечные.

### 3.6 Технические заметки

Здания хранятся как `shelter_buildings { building_id, player_id, slot, tier, built_at, durability, broken_at }`. Эффекты применяются в утреннем тике; крафт — отдельное действие с проверкой фазы (только утро–день). Клиент показывает сетку убежища 4+N слотов; анимация «строится» — CSS, без вебсокетов.

## MECH-04. Вылазки: ночные рейды (RD)

### 4.1 Назначение и дизайн-критерий

Вылазка — главное событие игрового дня: игрок ночью отправляет персонажа на карточную карту локации, проходит ноды, принимает решения и возвращается с добычей. Дизайн-критерий: одна вылазка = одна законченная «история» с началом, решениями и последствиями; риск встречи с враждебными NPC должен быть честным (шанс виден заранее) и наказывать агрессию моралью, а не только HP.

### 4.2 Формальные правила

**Доступ**: 1 вылазка за ночь (сумерки 20:00–21:00 — назначение; ночь 21:00–05:00 — исполнение сервером). Ограничения: персонаж `active`, энергия ≥25, не `hungry` 2-й стадии и хуже, не ранен тяжёло/болен критически (см. CH-02).

**Выбор локации** (4 локации, разные профили):

| Локация | Глубина (ноды) | Риск NPC | Профиль добычи | Доп. условие |
|---|---|---|---|---|
| Супермаркет | 8 | 25% | еда 40%, вода 30%, прочее | — |
| Аптека | 7 | 35% | медикаменты 50%, прочее | нужен фонарь |
| Промзона | 9 | 40% | материалы/parts 70% | нужен лом |
| Жилой квартал | 8 | 55% | смешанная, шанс торгового NPC 20% | — |

**Рюкзак**: база 12 кг (`strong` +5, сумка-крафт +3, итого до 20 кг). Каждый ресурс имеет вес: вода 0.5 кг/ед., сырая еда 0.4 кг, cooked_meal 0.3 кг, медикаменты 0.2 кг, материалы 0.1 кг, детали 0.15 кг, топливо 0.5 кг. Переполнение невозможно на сервере: взятие предмета сверх лимита отказывается (клиент показывает `weight: 11.4/12.0` и блокирует кнопку).

**Ноды**. Каждый нод — серверно сгенерированная карточка (детерминированный сид = `raid_session_id + нод_index`, генерация при создании сессии — клиент не может подсмотреть будущие ноды). Типы нодов:

| Тип нода | Шанс (супермаркет) | Действия игрока | Исходы сервера |
|---|---|---|---|
| Тайник | 45% | «обыскать» / «пройти мимо» | +ресурсы (вес!), шанс ловушки 10%: лёгкая рана |
| Завал | 20% | «разобрать» / «пройти» | +материалы, −5 энергии |
| Торговец | 15% | «торговать» / «пройти» | бартер по курсу локации (см. MKT) |
| Мирный NPC | 10% | «попросить» / «украсть» / «пройти» | см. MECH-06 |
| Враждебный NPC | 10% | «сдаться» / «отбиться» / «откупиться» | урон/потеря части добычи/мораль |

**Встреча с враждебным NPC** (шанс по таблице локаций на каждом ноде): исход считается сервером по формуле:

```
chance_win = base(0.5) + trait_bonuses + (energy/100)*0.1 - (npc_strength*0.1)
```

где `npc_strength` 1–3 по локации. При победе: добыча сохраняется, мораль −5 (насилие всегда стоит морали, TWoM [8]). При поражении: −30 HP, потеря 50% добычи. «Откупиться»: стоит 1 `cooked_meal` или 2 талона, 100% проход, мораль −2. «Сдаться»: потеря 30% добычи, мораль +3 (достоинство сохранено), лёгкая рана 20%.

### 4.3 Поток вылазки

![Поток вылазки](/docs/mechanics/assets/raid_flow.png)

Серверная сессия `raid_session`: создаётся в 20:00–21:00 со снимком (`snapshot` инвентаря до вылазки, чтобы торговля во время рейда не влияла на добычу); исполняется серией действий игрока (client intent → server validate → result); фиксируется в 05:00 или при досрочном выходе.

### 4.4 Edge cases

| # | Случай | Поведение |
|---|---|---|
| E1 | Персонаж умер во время вылазки (тяжёлая рана в ноде) | Нод обрывается, добыча до нода сохраняется, тело не возвращается (слот занят сутки, как при смерти в убежище) |
| E2 | Интернет пропал в середине вылазки | Сессия живёт на сервере; при восстановлении клиент синхронизирует текущий нод; авто-выход в 05:00 (E4 MECH-01) |
| E3 | Бустер x2 добычи активен | Множитель ×2 применяется к ресурсам нодов (не к весу); не стакается с собой; тратится 1 бустер на всю ночь |
| E4 | Все ноды пройдены до 05:00 | Вылазка завершается успешно, персонаж возвращается, бонус морали +5 («успешный рейд») |
| E5 | Игрок нажал «вернуться» на ноде 2 | Фиксация добычи до нода 2, штатное завершение, −10 энергии |

### 4.5 Доказательная база и адаптация

TWoM: одна вылазка на ночь на одну локацию, один выживший на локацию, ослабленные не ходят, опоздавшие к 05:00 возвращаются ранеными [2]; черты меняют рюкзак и стелс (Boris: 17 слотов −20% скорости, Arica: бесшумность) [2]; атака безоружных — моральный удар, тем сильнее, чем безоружнее жертва [8]. Адаптации: (а) ноды вместо свободного 2D-стелса — карточная механика под Mini App UI, (б) сид-детерминизм нодов на сервере — античит, (в) «откупиться» — наш третий вариант, снижающий фрустрацию новичков (в TWoM только драться/бежать).

### 4.6 Технические заметки

Действия вылазки — REST-эндпоинты `/api/raid/{session}/node/{n}/act`, каждый — транзакция с валидацией сессии (status=open, owner, фаза ночи). Генератор нодов — чистая функция от сида (тестируема unit-тестами на распределения). Веса и лимиты проверяются только на сервере. Клиент кэширует уже открытые ноды, никогда не запрашивает будущие.

## MECH-05. Ресурсы: типы, потребление, крафт еды (RES)

### 5.1 Назначение и дизайн-критерий

Ресурсы — топливо всей экономики: их нехватка создаёт давление, избыток — смысл торговли. Дизайн-критерий: игрок должен уметь пересчитать «сколько дней я проживу» по текущему складу — поэтому потребление задано простыми суточными нормами, а не скрытыми коэффициентами.

### 5.2 Формальные правила

**Типы ресурсов** и их роли:

| Ресурс | Роль | Источник | Редкость (старт) |
|---|---|---|---|
| `water` | Критическая: 1 сутки без воды = сразу Very Hungry | Вылазки, сборщик воды, рынок | Высокая |
| `raw_food` | Сырьё для еды | Вылазки, сад, ловушки | Средняя |
| `cooked_meal` | Потребляемая еда | Печь: 1 raw_food + 0.5 воды + 0.25 топлива | Производится |
| `meds` | Лечение болезней | Аптека (вылазка), рынок | Редкая |
| `bandage` | Раны | Крафт (аптечка/верстак) | Производится |
| `materials` / `parts` / `scrap` | Строительство, крафт | Вылазки (промзона), рынок | Средняя→редкая |
| `fuel` | Печь: готовка, отопление зимой | Вылазки, верстак (4 материала → 1 fuel) | Средняя |
| `trade_goods` | Торговля NPC (сигареты, алкоголь, табак) | Вылазки (жилквартал), рынок | Редкая |

**Суточное потребление на персонажа** (применяется в утреннем тике):

```
вода:   2.0 ед./сутки
еда:    1.0 cooked_meal (или эквивалент: 1 raw_food = «ещё голоден» — останавливает прогресс голода, но не откатывает стадию; 2 raw_food = 1 порция, как TWoM [4])
топливо: только при готовке (0.25/порцию)
```

Вода расходуется вдвое быстрее еды — наследие баланса Day R, где вода падает в 2 раза быстрее еды [3]. Это делает сборщик воды самым ценным стартовым зданием.

**Рецепт готовки** (печь, только утро–день):

```
cooked_meal = 1 raw_food + 0.5 воды + 0.25 fuel   (1 готовка на порцию; печь tier 2: 2/сутки)
```

Без печи `raw_food` можно съесть сырым: эффект «Still Hungry» (TWoM [4]) — голод не прогрессует сутки, стадии не откатываются.

**Хранение**: склад убежища — один общий пул на игрока (не на персонажа). Ёмкость растёт от сундуков-крафта (верстак: +20 слотов за 5 материалов; старт 50 слотов суммарно). Переполнение: новые ноды вылазки не принимаются, сервер отвечает `STORAGE_FULL` — игрок обязан продать/выбросить.

**Деградация**: сырая еда портится через 7 суток (`raw_food` → 0), вода не портится, топливо не портится. Портится FIFO. Это создаёт давление «готовь или теряй» и питает рынок (сливы излишков).

### 5.3 Балансовая проверка (симуляция 45 дней)

Скрипт `balance_sim.py` в репозитории моделирует 2 персонажей, 1 вылазку за ночь (9 нодов, лут-таблицы MECH-04), печь, сборщик воды, сад и ловушку. Результат: ни одной потери за 45 игровых дней, стабильный рост материалов (21 → 95), лёгкий дефицит топлива (игнорируемый в MVP — топливо производится из материалов). Дефицит воды к 30-му дню без апгрейда сборщика — это запланированный сигнал прогрессии, а не баг. При отключении ловушки и сада игрок выживает ~18 дней — «жёсткий режим» работает.

### 5.4 Edge cases

| # | Случай | Поведение |
|---|---|---|
| E1 | На складе 1 raw_food и 1 вода на 2 персонажей | Кто первый съел утром по порядку тика (персонажи тикаются по `created_at`); второй получает голод. Порядок стабилен — документирован |
| E2 | Игрок выбрасывает предмет | +мораль персонажам −1 на сутки («мы выбросили еду, пока другие голодали») — дешёвый слив запрещён |
| E3 | Портящаяся еда и активная готовка в один тик | Сначала готовка, потом порча (игрок спасает еду, если успел) |

### 5.5 Доказательная база и адаптация

TWoM: порция полной еды откатывает голод на стадию, 2 сырых продукта лишь останавливают прогресс [4]; топливо и вода участвуют в рецептах [7]. Day R: вода как ресурс вдвое быстрее еды [3]. LDOE: тирерные материалы [6]. Адаптации: (а) общий склад вместо инвентаря персонажей (упрощение для Mini App), (б) порча еды через 7 суток (в TWoM еда не портится — добавляем давление на рыночную ликвидность), (в) топливо как отдельный ресурс с конверсией из материалов (в TWoM топливо — лутаемый предмет).

## MECH-06. Мораль и психология: дилеммы (MOR)

### 6.1 Назначение и дизайн-критерий

Моральные дилеммы — наследие TWoM и главная причина, по которой игроки рассказывают истории об игре («я обокрал старика и мой персонаж впал в депрессию»). Дизайн-критерий: каждый выбор должен иметь **оба** последствия — немедленное (ресурсы) и отложенное (мораль/события), причём «плохой» выбор не наказан смертью, а «хороший» не награждён автоматически — только отложенные последствия делают выбор осмысленным.

### 6.2 Формальные правила

**Дилеммы генерируются сервером** в двух точках: (а) в вылазке на нодах «Мирный NPC» / «Враждебный NPC» (MECH-04), (б) в утреннем тике как редкие мировые события, затрагивающие конкретного игрока (шанс 3% в сутки, не чаще 1 раза в 3 суток на игрока).

Примерный каталог дилемм (минимум 12 в релизе, все с двумя последствиями):

| Дилемма | Вариант A | Вариант B |
|---|---|---|
| Старик просит еды | Отдать 1 cooked_meal → мораль +15 всем, шанс что он «отблагодарит» через 2–5 суток (+1 редкий предмет) | Прогнать → мораль −8 у решившего |
| Тайник с лекарствами в чужом убежище | Украсть meds → +3 meds, мораль −20 всем, риск рейда в ответ | Пройти мимо → мораль +5 |
| Незнакомец просится в группу | Принять → новый персонаж (слот), мораль +10, −30% эффективности 2 суток | Отказать → мораль −5, через 3 суток может появиться враждебным NPC (20%) |
| Раненый мародёр | Добить → +его лут, мораль −15, риск события «свидетель» | Помочь (бинт+meds) → мораль +12, шанс присоединится позже (10%) |
| Собственность погибшего соседа | Забрать всё → +материалы ×2, мораль −10 | Взять половину → +материалы, мораль +5 |
| Торговец предлагает краденое | Купить дёшево (−50% цена) → мораль −8 | Отказ → мораль +3, торговец запомнит (−10% курс навсегда) |

**Расчёт морали** (утренний тик):

```
morale_new = clamp(morale + Δ_выборы_за_сутки
                   − 5 × max(0, hunger_stage)        // голод
                   − 3 × (соседи в starving)          // TWoM: соседи грустят [4]
                   + 2 × (полный рацион 3+ суток)     // сытость восстанавливает
                   + 1 × (живёт в убежище с кроватью tier 2+))
```

Границы: `depressed` при <20, уход из группы при 0 (MECH-02). Мораль отображается в Mini App числом и текстовым статусом («в духе», «подавлен», «на грани»).

**Эффект депрессии на геймплей**: персонаж отказывается от вылазок (2 суток), уговаривается полным рационом + отдыхом. Персонаж с моралью <40 имеет +15% шанс ошибки в вылазке (промах в бою, шум).

### 6.3 Связь с MM-слоем

Моральные выборы с внешним эффектом («украсть из чужого убежища», MECH-04 E-варианты агрессивной экономики) — опция, включаемая после баланс-теста (по плану проекта). До включения: дилеммы затрагивают только NPC-мир. Все выборы пишутся в `character_events` и формируют «историю» персонажа, доступную в профиле — это реализация принципа TWoM «механики как фундамент нарратива» [5].

### 6.4 Доказательная база и адаптация

TWoM: атака безоружных снижает мораль тем сильнее, чем безоружнее жертва [8]; сытые персонажи не впадают в депрессию; голодающие соседи грустят [4]. Дизайн-уроки разработчиков: сила игры — в моральных решениях и их психологических последствиях, а моральные решения должны быть уважаемыми (без «gamism») [5]. Адаптации: (а) каталог дилемм фиксирован (12+) с балансной матрицей последствий — сервер знает все исходы заранее (античит), (б) отложенные награды («отблагодарит через 2–5 суток») реализованы как отложенные события в `world_events` с триггером по дню.

## MECH-07. Экономика игроков: рынок и талоны (MKT)

### 7.1 Назначение и дизайн-критерий

Общий рынок превращает одиночное выживание в MMO: избыток одного игрока — дефицит другого. Дизайн-критерий: сделка должна проходить только через сервер (двустороннее подтверждение: продавец выставил → покупатель нажал «купить» → атомарный обмен), а «талоны» — зарабатываемая валюта, чтобы F2P-игрок мог купить всё без Stars.

### 7.2 Формальные правила

**Валюта «талоны»**: мягкая валюта, заработок: продажа лотов на рынке, ежедневное задание «пережить сутки» (+5 талонов, 1 раз в сутки).Stars-пакеты талонов — хард-валюта (MECH-10). Начисление — только серверным тиком после webhook Stars, никогда клиентом.

**Лоты**: игрок выставляет ресурс X в количестве N за цену P талонов за единицу. Комиссия рынка 5% с продавца (удерживается при сделке, сжигается — дефляционный механизм). Лот живёт 3 игровых дня или до выкупа; снятие лота до выкупа — бесплатно.

**Матчинг**: в утреннем тике (06:00) сервер исполняет рынок: для каждого лота проверяет покупателей в порядке FIFO по цене (наивысшая цена первым); исполненные сделки пишутся в `transactions` атомарно (update seller balance + buyer inventory в одной транзакции с `SELECT ... FOR UPDATE`). Ночные покупки исполняются утром — правило MECH-01, пункт 3.

**Ценовые ориентиры** (баланс-референс, не хардкод): `cooked_meal` ≈ 10–15 талонов, `water` ≈ 5–8, `meds` ≈ 40–60, `materials` ≈ 2, `parts` ≈ 20, `scrap` ≈ 120. Сервер хранит агрегат «медианная цена за 7 суток» по каждому ресурсу и показывает его в UI лота («медиана: 12 талонов») — защита новичков от неликвида.

**Бартер с NPC-торговцами** (в вылазке и утром): каждый NPC-торговец имеет матрицу курса: базовая стоимость предмета (как TWoM: медикаменты 32, бинты 27.5, сырая еда 9, вода 1) и коэффициент выкупа 0.6–0.85 по локации [9]. Обмен детерминированный: `талон-эквивалент = round(base_value × locale_coeff)`. Черта `negotiator` даёт +10% к талон-эквиваленту.

### 7.3 Edge cases

| # | Случай | Поведение |
|---|---|---|
| E1 | Гонка: 2 покупателя одного лота | FOR UPDATE в транзакции: исполнится первый зафиксированный, второй получит `LISTING_SOLD` и возврат |
| E2 | У продавца не хватает ресурса при исполнении (продал дважды) | Невозможно: лот резервирует количество в `market_listings` (холд), холд снимается при снятии лота/исполнении/истечении |
| E3 | Рынок пуст (мало игроков) | Бот-NPC «склад» с фиксированной матрицей (±20% от медианы) обеспечивает ликвидность минимумом |
| E4 | Обвал рынка (мировое событие EVT-03) | Цены на выбранный ресурс ×0.5 глобально на 1 сутки; лоты остаются, исполняются по новым ценам |

### 7.4 Доказательная база и адаптация

TWoM: чистый бартер без валюты, матрица базовых стоимостей из данных игры, коэффициенты выкупа трейдеров 0.62–0.83, наценка ~20% без навыка торговли [9] [10]. Адаптации: (а) добавляем валюту «талоны» — чистый бартер не масштабируется на N игроков без O(N²) парных сделок; (б) двусторонний матчинг с FIFO и комиссией — стандарт игровых аукционов; (в) медианная цена в UI — против манипуляций новичками; (г) NPC-ликвидность — против пустого рынка на старте (проблема всех MM-аукционов).

## MECH-08. Группы и кланы (GRP)

### 8.1 Назначение и дизайн-критерий

Группа = общее убежище нескольких игроков: совместное выживание как социальный клей Telegram. Дизайн-критерий: приглашение — через бота (`/invite`), управление — в Mini App, а выход из группы не должен обнулять прогресс игрока (человеческая цена выхода — потеря общего склада, но свои персонажи и здания переносятся).

### 8.2 Формальные правила

**Создание**: игрок с 5+ игровыми сутками создаёт группу (лимит групп на игрока = 1). Лимит группы: 2 (лидер) + 4 участника.

**Роли**: `leader` (всё), `officer` (приглашения, склад), `member` (свои персонажи, доступ к складу только по выделению). Смена лидера — только передача участнику; при неактивности лидера 7 суток лидерство переходит старшему офицеру автоматически (защита от «бросившего» лидера).

**Общий склад**: пул ресурсов группы, доступ по ролям. Взнос: игрок передаёт со своего склада на общий (обратимо в течение 1 суток — «окно сомнений», потом необратимо). Выдача: офицер+ назначает ресурсы игроку.

**Совместные вылазки**: в группе доступна «групповая вылазка» (1 на ночь вместо индивидуальной): 2 персонажа от разных игроков на одну карту, рюкзак суммарный (24 кг база), глубина +2 нода. Дележ добычи — поровну по умолчанию, лидер может настроить доли (минимум 10% каждому).

**Общее убежище**: здания группы строятся на общий счёт группы (ресурсы участников по взносу). При выходе игрока его личные постройки конвертируются в материалы (50% на личный склад), общие — остаются.

**Чат группы**: не делаем свой чат — группа Telegram-чата игры и так существует; бот шлёт групповые уведомления (начало ночи, сводка) в чат группы.

### 8.3 Edge cases

| # | Случай | Поведение |
|---|---|---|
| E1 | Игрок исключён из группы | Окно сомнений 1 сутки на его взносы, персонажи его, склад группы — нет доступа с момента исключения |
| E2 | Группа распущена (лидер ушёл, офицеров нет) | Ресурсы общего склада делятся поровну по последним суточным взносам; постройки конвертируются в материалы по доле |
| E3 | Игрок в группе и вне её одновременно | Запрещено: вступление в группу = автоматический выход из предыдущей с уведомлением |

### 8.4 Доказательная база и адаптация

План проекта фиксирует `/invite` через бота и роли лидер/участник; State of Survival демонстрирует, что альянсы — ключевой ретеншн-фактор 4X, но у нас упрощённая версия без войны альянсов [11]. Адаптации: (а) «окно сомнений» на взносы — против импульсивной потери ресурсов, (б) автоматическая передача лидерства — против заброшенных групп, (в) дележ с минимумом 10% — против токсичного лидерства.

## MECH-09. Мировые события (EVT)

### 9.1 Назначение и дизайн-критерий

Мировые события — серверные «погодные» явления, которые касаются всех игроков одновременно и создают общие разговоры («пережили набег?»). Дизайн-критерий: событие должно быть предсказуемо по формату, но не по дате; последствия — корректирующими (±), а не обнуляющими.

### 9.2 Формальные правила

События планируются сервером: каждое имеет тип, шанс в сутки (после 10-го игрового дня), длительность и глобальный модификатор. Расписание не детерминировано (сид по `world_day`), чтобы сообщество не могло предсказать дату, но мог проверить постфактум.

| Событие | Шанс/сутки | Длительность | Эффект | Контрмера игрока |
|---|---|---|---|---|
| «Холодный фронт» | 4% | 2 суток | Потребление топлива ×2; вода в сборщиках −50% | Запас топлива, укрытие (постройка tier 2+) −25% эффекта |
| «Набег мародёров» | 3% | 1 сутки | Случайный игрок (из активных за сутки) теряет 10% материалов склада; здания −1 durability | Группа: патруль (2 персонажа ночью) снижает шанс на 70% |
| «Обвал рынка» | 2% | 1 сутки | Медианная цена одного ресурса ×0.5 | Не выставлять лоты этого ресурса сутки |
| «Щедрость выживших» | 3% | 1 сутки | +1 cooked_meal каждому активному игроку; мораль +5 | — |
| «Эпидемия» | 1% | 3 суток | Шанс болезни при грязной воде ×2 | Аптечка tier 2+, запас meds |
| «Перемирие на рынке» | 2% | 2 суток | Комиссия рынка 0% | Выставлять крупные лоты |

**Механика «набега мародёров» (подробно)**: сервер выбирает цель равномерно среди игроков, игравших последние 24 часа (офлайн-игроки не наказываются — защита от наказания за жизнь вне игры). Уведомление жертве ботом и в Mini App: «Мародёры обчистили ваш склад: −{N} материалов». Игрок с групповым патрулём (MECH-08) — шанс попасть в цель ×0.3.

**Журнал**: каждое событие пишется в `world_events { day, type, affected_player_id?, params }` и отображается в ленте новостей Mini App (последние 7 суток).

### 9.3 Доказательная база и адаптация

TWoM: погода и новости радио меняют цены и доступность ресурсов (топливо и дерево дорожают в холода) [10] — наш «Холодный фронт». План проекта называет «обвал рынка» и «набег мародёров» как референсные события. Адаптации: (а) офлайн-защита (нет наказания за отсутствие — ключевое отличие от «жестоких» MMO), (б) контрмеры в каждой механике (патруль, запас топлива) — события наказывают беспечность, а не наличие.

## MECH-10. Монетизация Stars (MON)

### 10.1 Назначение и дизайн-критерий

Монетизация — официальная, через Telegram Bot Payments API (Stars/XTR). Дизайн-критерий: жёсткий запрет pay-to-win — покупка даёт только время, косметику и расширение; любой ресурсный бустер ограничен по длительности и масштабу, чтобы симуляция (MECH-05) оставалась валидной и для платящих.

### 10.2 Каталог товаров

| Товар | Цена (XTR) | Эффект | Ограничение |
|---|---|---|---|
| 500 талонов | 50 | +500 талонов | Лимит 3 пакета/сутки |
| 2500 талонов | 200 | +2500 талонов | Лимит 1/сутки |
| Скин убежища «Сумерки» | 100 | Визуальная тема Mini App | Навсегда |
| Скин персонажа ×3 | 75 | Визуал карточки персонажа | Навсегда |
| Бустер «Двойная добыча» | 150 | ×2 ресурсы нодов вылазки | 1 вылазка |
| Бустер «Быстрый крафт» | 100 | Строительство/крафт без суточной задержки | 1 действие |
| Слот персонажа (+1, макс 5) | 300 | +1 слот персонажа | Навсегда, макс 5 |
| Слот группы (+2, макс 8) | 500 | Группа до 8 | Навсегда |
| Пропуск болезни | 120 | Снять статус болезни | 1 персонаж, 1 раз/сутки |
| Подписка «Припасы месяца» | 499/мес | +10% ко всем доходам, скин-рамка, ежедневный бонус 20 талонов | Stars-подписка API |

### 10.3 Поток оплаты (атомарность)

1. Клиент запрашивает товар → сервер создаёт invoice-линк (`createInvoiceLink`, валюта XTR) и записывает `star_payments { idempotency_key = telegram_payment_charge_id, player_id, product, status=pending }`.
2. Mini App открывает оплату (`openInvoice`).
3. Telegram шлёт webhook `successful_payment` → бэкенд валидирует HMAC (`X-Telegram-Bot-Api-Secret-Token`) и ищет запись по `telegram_payment_charge_id`.
4. При совпадении `pending` → исполнение товара и статус `completed`; повторный хук с тем же charge_id — no-op (идемпотентность по unique-ключу, критерий приёмки плана).
5. `refunded_payment` → возврат товара (если обратим) и статус `refunded`; при невозможности отката (бустер использован) — отказ в возврате с уведомлением.

**Запреты баланса**: бустеры не действуют на рынок и групповые механики; подписка «+10% доходов» применяется до комиссии, не после; талоны из Stars-пакетов не передаются другим игрокам (только тратятся).

### 10.4 Доказательная база и адаптация

План проекта фиксирует паттерн `createInvoiceLink` + `openInvoice` + `successful_payment` с идемпотентностью по charge_id — это официальный Bot Payments API. Монетизация «время/косметика, не сила» — отраслевой стандарт F2P и требование модерации Telegram Mini Apps.
